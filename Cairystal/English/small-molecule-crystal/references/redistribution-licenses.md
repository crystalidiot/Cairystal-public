# 软件依赖与发布包的许可核对

在准备 GitHub 发布、源码 ZIP、离线安装包或打包 EXE 时阅读；普通晶体解析不需要每次重新执行此流程。根目录的 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md) 和 `licenses/` 应随 skill 分发，并纳入文件清单与哈希。保留已核对的旧版本，更新内容后另建发布记录。

## 当前源码包

当前模式只发布 Cairystal skill 源码与文档，Gemmi 等库由使用者另行安装。不要把工作站的整个 venv、site-packages、软件目录、许可凭据或晶体数据打包进去。写清第三方名称、已核对版本、许可证、官方项目和对应版本源码入口；将实际运行依赖版本写入 profile。只声明已经核对的范围，不能由一个 Gemmi 条目推断所有依赖已获再分发授权。

Gemmi 0.7.5 的本次声明选择 MPL-2.0。上游 README 同时提供 LGPLv3 选项，不能把这一选择误写成上游仅有一种许可，也不要把 Gemmi 的 MPL 文本作为 Cairystal 全项目的许可证。

## 如果以后捆绑 Gemmi

1. 列出实际随包文件、版本、来源、哈希和是否修改。直接下载官方包的安装器，与已经内含库文件的离线包是不同分发模式。
2. 保留 Gemmi 的许可全文、原有版权声明和适用的第三方许可声明。按该构建实际包含的组件核对，不以最新网页或本机另一个版本替代。
3. 对分发的 Gemmi 可执行形式，明确告诉接收者如何及时、合理地获得对应源码。原版可指向可用的匹配版本上游源码；为降低链接失效风险，可同时保存对应源码归档。记录实际下载和核对结果，不能把未访问的归档链接写成已下载或已校验。
4. 若修改了 MPL 覆盖的文件，提供包含修改的相应源码并维持 MPL 条件；只指向未修改的上游版本不够。不要把修改 Gemmi 源码与独立编写、调用其 API 的 Cairystal 文件混为一谈。
5. 检查安装器或自己的 EULA 不限制接收者对 MPL 覆盖源码的权利。不能暗示上游作者为 Cairystal 背书。
6. 实际打开最终 ZIP/安装包，确认声明、许可全文、对应版本源码说明都在，核对哈希；没有完成的依赖审查应标为待核对，不能声称整包已获得法律保证。

这份文档是发布操作记录要求，不是对任何未知打包方式的法律结论。涉及商业合同、修改后闭源分发或不确定组合时，需要针对实际文件核对许可。
